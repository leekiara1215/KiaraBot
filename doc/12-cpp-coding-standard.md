# KiaraBot C++ 主编码规范

- **状态**：仓库主规范
- **适用范围**：`core/` 以及仓库内所有手写 C++ 源码
- **语言基线**：C++20
- **最后更新**：2026-10-29

本文件是 KiaraBot C++ 代码的统一约定。它综合 C++ Core Guidelines、Google C++ Style Guide 和 LLVM Coding Standards，并按 KiaraBot 的模块边界、协议和工具链做了明确取舍。目标是让代码容易阅读、测试、替换和审查。

## 1. 必须遵守的仓库约定

### 1.1 构建和语言

- 使用 C++20；不得为了单个实现偷偷引入更高版本特性。
- 使用 CMake 管理构建；不得把本机绝对路径写入 CMake、源代码或配置文件。
- 编译必须保持无警告目标：Clang/GCC 至少开启 `-Wall -Wextra -Wpedantic`，MSVC 开启 `/W4`。
- 公共跨进程接口必须在 `proto/` 中定义；不能把 C++ 类、指针或内部头文件当作跨语言接口。
- Protobuf/gRPC 生成源码属于生成物，不能手工编辑，也不应把生成目录提交到仓库。

### 1.2 模块边界

- `core/` 不得依赖 NoneBot2、NapCat、Python 运行时、浏览器代码或第三方模型 SDK。
- 适配器不得把平台原始事件、平台数据表或第三方 SDK 对象泄漏到 Core。
- 插件不得直接访问数据库、OneBot 或 Core 内部类，必须通过 PluginSDK。
- 控制面板不得实现消息路由、权限规则或 AI 业务逻辑。
- Core 通过端口依赖基础设施；业务代码不得直接写 SQL 或持有数据库连接。
- 跨模块修改按“先协议/接口、后实现、再测试”的顺序进行。

### 1.3 目录和文件

手写 C++ 文件使用以下命名：

```text
目录：snake_case/
头文件：snake_case.hpp
源文件：snake_case.cpp
测试：同名组件 + _test.cpp，或放在对应 tests/ 目录
```

现有目录有其他命名时，不为了改名进行无关重构。Protobuf 文件保持协议既有命名；生成的 `.pb.h`、`.pb.cc`、`.grpc.pb.*` 不手工修改。

## 2. 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 命名空间 | 小写 `snake_case` | `kiarabot::core` |
| 类、结构体、枚举类型 | `PascalCase` | `EventRouter`、`ActionResult` |
| 函数、方法 | 小写 `snake_case` | `publish_event()` |
| 局部变量、参数 | 小写 `snake_case` | `event_id` |
| 非静态数据成员 | 小写 `snake_case` 加尾部下划线 | `trace_id_` |
| 常量、`constexpr` 变量 | `kPascalCase` | `kMaxRetries` |
| 枚举项 | `PascalCase` | `DeliveryStatus::Pending` |
| 宏 | 全大写并带项目或模块前缀 | `KIARABOT_ENABLE_PROTO` |
| 模板参数 | `PascalCase` | `typename ValueType` |

- 名称必须表达用途，避免 `data`、`info`、`tmp`、`foo` 等无上下文名称。
- 缩写按一个单词处理：`HttpClient`、`user_id`，不要混用 `HTTPClient`、`userID`。
- 不使用匈牙利命名法，不用类型信息污染变量名。
- 不使用 `using namespace ...;`，尤其不能在头文件中使用。
- 新增公共 API 时优先采用仓库规则，即使第三方库使用另一种命名风格。

## 3. 格式

格式由根目录 [`.clang-format`](../.clang-format) 自动化执行；提交前应运行：

```bash
clang-format --dry-run --Werror <changed-cpp-files>
```

固定规则如下：

- 2 个空格缩进，不使用 Tab。
- 大括号与控制语句、函数声明同行（Attach 风格）。
- 目标列宽 100。
- 指针和引用靠近类型：`const std::string& name`、`Node* node`。
- 每个源文件以换行符结束。
- 单条语句也保留大括号，避免后续添加语句时引入错误。
- `#include` 顺序：对应源文件头文件、C++ 标准库、第三方库、仓库头文件；各组之间空一行。
- 头文件使用 `#pragma once`，不重复包含自身依赖。
- 不提交编辑器自动生成的格式差异或无关的全文件重排。

推荐的文件开头：

```cpp
#include "kiarabot/core/event_router.hpp"

#include <string>
#include <string_view>

#include <third_party/library.hpp>

#include "kiarabot/core/event.hpp"
```

## 4. 类型、常量和表达式

- 优先使用标准库类型：`std::vector`、`std::array`、`std::string`、`std::string_view`、`std::span`。
- 使用 `nullptr`，不得使用 `NULL` 或整数 `0` 表示空指针。
- 使用 `enum class`，除非必须兼容已有 C 接口或协议生成代码。
- 使用 `const` 表达不修改的对象和成员函数；能在编译期求值时使用 `constexpr`。
- `auto` 仅在类型明显、冗长或依赖模板推导时使用；不要让 `auto` 隐藏重要的所有权或数值类型。
- 避免隐式窄化转换、有符号/无符号混用和未经说明的整数转换；必要时使用显式转换并在代码中表达意图。
- C++ 强制转换使用 `static_cast`、`const_cast`、`reinterpret_cast` 或 `dynamic_cast`，不得使用 C 风格 `(Type)value`。
- 不用宏实现常量、函数或复杂控制流；宏仅用于编译开关、平台兼容或必要的生成接口，并带 `KIARABOT_` 前缀。

## 5. 所有权和生命周期

- 采用 RAII；资源必须由对象的生命周期管理。
- 默认使用值语义；需要独占所有权时使用 `std::unique_ptr`，只有确实共享所有权时使用 `std::shared_ptr`。
- 裸指针和引用只表达“观察”或“非拥有”关系；接口文档必须让所有权清晰。
- 使用 `std::make_unique`、`std::make_shared`，避免直接 `new` 和 `delete`。
- 不返回指向局部变量、临时对象或已释放资源的指针/引用/`std::string_view`。
- 不把 `std::shared_ptr` 当作默认参数类型；先确认是否真的存在共享生命周期。
- 类优先遵循 Rule of Zero；需要自定义析构、复制或移动操作时，明确写出并测试其语义。
- 锁、文件、事务、网络连接等资源必须有明确的获取和释放边界，异常或提前返回不能泄漏资源。

## 6. 类和接口设计

- 一个类只负责一类职责；业务规则放在 Core 的领域或应用层，不放在适配器和 UI 中。
- 成员变量默认 `private`；公共接口尽量小而稳定。
- 构造函数使用成员初始化列表；单参数构造函数默认加 `explicit`。
- 重写虚函数必须写 `override`；禁止用注释代替 `override`。
- 作为多态基类时，析构函数声明为 `virtual`；不允许通过基类指针销毁的类应明确禁止这种用法。
- 传递只读的大对象使用 `const T&`；小型、廉价类型按值传递；需要可选值时使用 `std::optional<T>`。
- 不用输出参数表达普通返回值；优先返回值或明确的结果对象。
- 不把可变全局变量、单例或静态状态作为模块间通信机制。
- 公共接口的错误、超时、幂等和线程安全语义必须在头文件注释或对应模块文档中说明。

## 7. 错误处理和日志

- 预期的业务拒绝、权限不足、重复事件、校验失败使用显式结果和稳定错误码，不用异常作为正常控制流。
- 异常不能跨进程边界、协议边界或插件边界传播；边界层必须捕获并转换为稳定错误。
- 在仓库统一结果类型落地前，不要在不同模块各自发明互不兼容的 `Result` 类型；沿用现有接口并在任务中先补充公共类型。
- 失败路径必须保留必要上下文，包括 `trace_id`、对象标识和可操作的错误原因；不得记录密码、令牌、API Key 等秘密。
- 析构函数不得抛出异常；清理失败必须通过日志、状态或显式关闭接口处理。
- `assert` 只用于检查程序内部不变量，不用于验证外部输入、权限或网络数据。
- 日志使用结构化字段；不要通过字符串拼接隐藏关键字段，也不要在循环中无控制地输出高频日志。

## 8. 并发和异步

- 先定义数据所有权和线程归属，再引入锁或异步任务。
- 不在持有锁时调用未知代码、网络服务、插件或用户回调。
- 锁的作用域尽量短；使用 RAII 锁对象，不手工 `lock()`/`unlock()` 配对。
- 明确任务取消、超时、关闭和对象生命周期；异步回调不能捕获已失效的引用。
- 不以“加一个全局 mutex”掩盖不清晰的状态模型。

## 9. 测试

- 新增或修改业务行为必须同时补充测试；纯格式修改可以不新增测试。
- 测试名称表达场景和预期结果，优先覆盖成功、拒绝、重复、超时、取消和依赖故障路径。
- Core 测试不得依赖真实 NapCat、NoneBot、模型服务或生产数据库；使用模拟适配器、内存存储或测试桩。
- 协议变更必须验证字段编号、兼容性、序列化/反序列化和错误语义。
- 测试不能依赖执行顺序、网络、当前时间或本机目录；需要时注入时钟、随机数和文件系统。
- 基础验证命令：

```bash
cmake --preset dev
cmake --build --preset dev
ctest --preset dev
```

启用协议生成时使用：

```bash
cmake --preset proto
cmake --build --preset proto --target kiarabot_proto
ctest --preset proto
```

## 10. AI 开发流程

任何 AI 代码任务按以下顺序执行：

1. 阅读根目录 `AGENTS.md`、本文件，以及目标模块文档。
2. 确认目标模块、责任边界、允许修改的目录和验收命令。
3. 先检查现有接口、测试和 CMake 目标，再设计最小改动。
4. 先修改公共协议或接口，再修改实现和测试；避免无关重构。
5. 对新增代码运行 clang-format、编译和相关测试。
6. 检查 `git diff`，确认没有生成物、密钥、构建目录或无关格式变化。
7. 在交付说明中列出改动文件、行为变化、实际运行的命令和未运行检查的原因。

AI 不得：

- 未阅读本文件就开始写代码；
- 为了通过测试删除断言、放宽校验或吞掉错误；
- 未经任务需要修改公共协议、依赖版本或模块边界；
- 复制第三方源码或把外部服务实现塞进 Core；
- 在没有说明的情况下引入裸 `new`/`delete`、全局可变状态或线程分离任务；
- 把“代码能编译”当作完成，忽略测试、错误语义和资源生命周期。

## 11. 允许的例外

以下内容可以不完全遵守手写 C++ 规则，但必须保持边界清晰：

- Protobuf、gRPC 或其他工具生成的源码；
- 第三方库和 vendored 代码；
- 与外部 ABI、C API 或操作系统接口对接的兼容层；
- 为兼容现有协议或旧数据而保留的遗留代码。

例外应限制在最小目录或函数范围，并在代码注释、模块文档或变更说明中写明原因。不要为了迁就例外扩散新的风格。

## 12. 提交前检查清单

- [ ] 已阅读本规范和目标模块文档。
- [ ] 修改仍位于正确模块，依赖方向没有反转。
- [ ] 所有权、生命周期、错误和线程安全语义清晰。
- [ ] 没有裸拥有指针、未说明的全局状态或跨边界异常。
- [ ] 已运行 clang-format 或确认变更不涉及 C++ 格式。
- [ ] 已运行相关构建和测试，并记录结果。
- [ ] `git diff` 中没有构建产物、生成源码、密钥和无关变更。
