# 控制面板 API 契约补充任务说明

- **状态**：T08a 已于 2026-10-30 完成契约决策；下文保留历史交接问题，不代表现行规范。
- **目标**：消除控制面板 API 第一阶段使用 mock Core 时遇到的契约阻塞，并明确未来接入真实 Core 前其他模块需要完成的工作。
- **现行唯一来源**：api/openapi.yaml、api/asyncapi.yaml；冻结结果与同进程端口见 doc/06-control-api.md 的 T08a 章节。历史验收清单保留未勾选，运行服务的验收仍属 T08b/T09，不能用契约完成替代服务完成。

## 当前依据与责任边界

- REST 契约以 [`api/openapi.yaml`](../api/openapi.yaml) 为唯一来源；实时协议以 [`api/asyncapi.yaml`](../api/asyncapi.yaml) 为唯一来源。控制 API 的职责和现有要求见 [`doc/06-control-api.md`](06-control-api.md)。
- [`proto/kiarabot/v1/services.proto`](../proto/kiarabot/v1/services.proto) 当前只声明适配器和插件桥接服务，尚未声明控制面管理服务。Core 拥有权限、插件状态和审计等业务状态，见 [`doc/02-core.md`](02-core.md)。
- **契约负责人**负责确认并更新 OpenAPI、AsyncAPI 和必要的 Protobuf 契约及兼容性验证；**Core 负责人**负责确认 Core 端口、事务和事件语义，并在后续实现其服务；**控制 API 负责人**在契约冻结后实现协议映射和 mock Core 集成测试。具体改动由对应模块另行安排，不由本文代替授权。
- 控制 API 不直接访问数据库表、NapCat、插件进程或模型 Provider，也不向插件下发管理员 token。真实 Core 服务不是第一阶段 mock 的前置实现，但 mock 端口必须遵循已确认的行为。

## P0：解除第一阶段契约阻塞

### 1. 会话查询和撤销

**责任**：契约负责人确认 REST 形状和错误语义；认证/会话状态的所有者与 Core 负责人共同确认存储、撤销和审计边界；控制 API 负责人在冻结后实现。

**现状**：OpenAPI 只声明登录和刷新，没有撤销操作，也没有供管理员定位会话的接口；控制 API 文档要求管理员能撤销会话。

**建议确认**：

- 增加 `GET /auth/sessions`，以 bearer token 查询可管理的会话。响应建议包含 `items`、`page`，每项包含 `session_id`、用户标识、创建时间、过期时间和状态；不返回 token 或 token 哈希。确认用户是否可以查询自身会话。
- 增加 `POST /auth/sessions/{sessionId}/revoke`，要求 bearer token 和 `Idempotency-Key`；建议成功返回 `204`。确认会话不存在和已撤销时的行为，建议对已知且已撤销的会话返回 `204`，对不存在的会话返回 `404`。
- 确认 `TokenPair` 是否返回 `session_id`，以及 refresh token 轮换后 session ID 是否保持不变。只返回当前登录会话 ID 无法单独满足管理员撤销其他会话，需要确定查询或其他发现机制。
- 明确撤销对 access token、refresh token 和现有 WebSocket 连接的生效范围及延迟，管理员撤销和失败请求的审计要求。

**建议错误**：缺失或无效凭据为 `401 / UNAUTHENTICATED`；无权限为 `403 / PERMISSION_DENIED`；目标不存在为 `404 / NOT_FOUND`；会话依赖不可用为 `503 / UPSTREAM_UNAVAILABLE`。所有 REST 错误使用现有 `Error` schema。

**验收**：

- [ ] 管理员能定位和撤销目标会话；无权限用户被拒绝；重复撤销无重复副作用。
- [ ] 撤销后 access token、refresh token 和 WebSocket 按确认的时限失效；不存在会话和依赖故障按契约返回错误。
- [ ] 生成客户端能调用新增操作并处理所有声明的响应；撤销产生约定的审计记录。

### 2. REST 错误、幂等和 token 轮换

**责任**：契约负责人负责操作级响应声明及跨协议错误映射；Core 负责人确认依赖故障、超时和写入结果未知时的语义；控制 API 负责人实现映射。

**现状**：多个操作没有声明实际可能出现的响应，例如列表未声明无效分页的 `400` 和 Core 不可用的 `503`，插件配置更新未声明目标不存在的 `404`。现有幂等参数要求 24 小时内重放原响应，但没有定义与 refresh token 旋转及撤销的交互。

**建议确认**：

- 按每个操作补充适用的响应，而不是假设所有操作都会产生所有状态。复用 `Error` schema，并明确 `request_id`、`trace_id`、`retryable` 和不泄漏敏感信息的要求。
- 建议映射：输入或分页 token 无效 `400 / INVALID_ARGUMENT`；凭据失效 `401 / UNAUTHENTICATED`；权限不足 `403 / PERMISSION_DENIED`；资源不存在 `404 / NOT_FOUND`；版本、状态或同键不同请求冲突 `409 / CONFLICT`；限流 `429 / RATE_LIMITED` 并提供 `Retry-After`；内部故障 `500 / INTERNAL`；Core 不可用 `503 / UPSTREAM_UNAVAILABLE`。确认 `TIMEOUT` 的 HTTP 状态和重试语义，并与 [`doc/01-contracts.md`](01-contracts.md) 的 gRPC 映射协调。
- 确定幂等键的主体、方法、路径和请求体作用域，规范化与比较规则、并发执行保证、24 小时内缓存哪些成功和失败，以及超时后结果未知时如何安全重试。
- 定义未认证登录请求的幂等作用域和认证失败、限流、审计行为。refresh 成功后旧 token 失效；建议同一幂等请求重放首次结果，不同键重用旧 token 返回 `401`。
- 明确缓存的 token 响应保护和清除方式，以及会话撤销后的重放行为。建议撤销后不再返回已失效会话的 token，作为原响应重放规则的明确例外，避免削弱撤销。

**验收**：

- [ ] 操作级契约覆盖适用的 `400/401/403/404/409/429/500/503`，错误结构和稳定码可由生成客户端处理。
- [ ] 并发重复写只产生一次副作用；同键不同请求返回约定冲突；超时后的重试行为可验证。
- [ ] 登录、刷新、旧 refresh token 重用和撤销后重放符合最终确认的安全与幂等规则。

### 3. 分页、一致性和排序

**责任**：契约负责人确认 REST 参数与响应；Core 负责人确认资源版本、快照和稳定排序能力；控制 API 负责人负责 token 和映射实现。

**建议确认**：

- 明确 token 绑定认证主体、资源、已声明过滤条件、排序、页大小及资源版本或快照；当前契约没有过滤参数，新增过滤条件需先定义参数。
- 明确 token 篡改、过期、跨主体或跨条件使用时的错误，建议 `400 / INVALID_ARGUMENT`；定义资源变化后继续读取一致快照还是使 token 失效。
- 末页建议省略 `next_page_token`，而非返回当前字符串 schema 未允许的 `null`。默认 20、最大 100 的现有约束保持明确。
- 为每类列表指定可用的稳定排序。现有文档要求 `created_at, id`，但 Adapter、Plugin 没有 `created_at`，AuditEntry 使用 `occurred_at`；需增加字段或确认各自排序规则。

**验收**：

- [ ] 默认、边界页大小及末页响应符合契约；稳定分页无重复或遗漏。
- [ ] token 跨主体、资源、条件及过期使用被拒绝；资源变化后的行为符合选定的快照策略。

### 4. WebSocket 握手、恢复和 resync

**责任**：契约负责人更新 AsyncAPI；Core 负责人确认事件与快照水位能力；控制 API 负责人实现 WSS、授权过滤和恢复。

**现状**：AsyncAPI 已声明客户端 `hello`、`resume`、流事件和 `RESYNC_REQUIRED`，但控制 API 文档要求的服务端 `session_id` 和 `last_sequence` 确认消息没有 schema。

**建议确认**：

- 增加独立服务端确认 message/schema，纳入 control 频道的订阅消息。建议响应包含 `type`、`session_id`、`last_sequence`；例如 `{"type":"SESSION_READY","session_id":"...","last_sequence":123}`。这些名称和值均需负责人确认。
- 定义 `hello.last_sequence` 的用途，`last_sequence` 是当前服务端水位还是已交付水位，序列号是全局还是按频道，以及确认帧、重放事件和实时事件的顺序。明确客户端去重和重放边界。
- `resume` 必须重新认证并验证会话归属和当前权限，不能仅凭 `session_id` 授权。统一 HTTP 升级 bearer 认证、`hello.access_token` 和浏览器认证方式；明确 token 到期与会话撤销后连接如何处理。
- 明确十分钟保留窗口、`RESYNC_REQUIRED` 的稳定原因及发送后连接是否关闭。定义 REST 快照如何返回或关联可恢复的事件水位，避免客户端拉快照时漏掉事件。
- 确认 control 与 health、logs、adapters、plugins、tasks、messages 是独立路径还是单连接逻辑频道，明确订阅及逐频道权限过滤。
- 明确升级前认证失败的 HTTP 响应，以及升级后的无效首帧、权限不足和内部故障使用的消息或 WebSocket close code。生产使用 WSS，开发例外以确认后的契约为准。

**验收**：

- [ ] `hello` 和 `resume` 的请求及服务端确认都符合 schema；窗口内按约定顺序恢复并处理重复事件。
- [ ] 过期游标或无法保证连续性时触发 resync；快照与事件水位衔接，不遗漏快照期间的事件。
- [ ] 无效凭据、跨用户恢复、无频道权限、token 过期和会话撤销均按契约处理；生成客户端兼容。

### 5. 权限矩阵和审计

**责任**：Core 负责人确认权限和业务审计规则；契约负责人公开客户端可见语义；控制 API 负责人在每个入口执行授权并记录其负责的操作。

**建议确认**：为每个 REST 操作和 WebSocket 频道列出权限及管理员、运维、只读角色的默认权限；无匹配策略默认拒绝。重点确定用户、日志、审计、插件配置及消息内容的读取范围和脱敏要求。

审计建议包含操作者、操作、目标、发生时间、请求/链路 ID、结果和稳定错误码；不得记录密码、token、密钥或完整敏感配置。需决定成功、失败和拒绝请求的记录责任，及审计不可用时写操作是否拒绝。若客户端需要查询结果字段，需同步扩展 `AuditEntry`。

**验收**：

- [ ] 每个操作覆盖允许与拒绝；未知角色和缺失策略默认拒绝；普通用户不能读取未授权消息或敏感配置。
- [ ] 每个写操作按最终规则审计，重复幂等请求不重复产生业务副作用；日志、审计和响应不泄漏凭据。

## P1：真实 Core 对接前完成

### 6. 控制面查询和插件管理协议

**责任**：协议负责人和 Core 负责人定义并实现跨进程公共接口；控制 API 只依赖生成的协议和确认的端口。此项不是 mock Core 第一阶段的真实服务实现前置条件。

**建议接口**：

- 查询机器人、适配器、插件、模型、群组、用户、任务、日志、审计和健康。请求包含可信操作者上下文、分页和已声明过滤条件；响应包含资源、下一页 token 及一致性版本或快照标识。
- 插件 manifest 验证、启用、停用、配置读取和按 `expected_version` 更新、健康查询。写请求包含操作者、`request_id`、`trace_id`、幂等键和适用 deadline。
- 明确 REST `202` 对应 Core 的“已接受”而非“已完成”，以及最终状态的查询或事件通知方式。定义配置冲突、重复执行、超时和结果未知时的处理。
- 复用现有 `kiarabot.v1.Error` 和稳定错误码，明确 gRPC 状态与错误详情映射；不将内部异常或凭据暴露给客户端。

**验收**：

- [ ] mock 与真实 Core 遵循同一已确认端口语义；覆盖插件启停、版本冲突、重复写、超时和 Core 不可用。
- [ ] Protobuf descriptor 兼容性、生成代码及跨语言序列化测试通过；生成物不提交。

### 7. Core 授权、审计和事件流端口

**责任**：Core 负责人定义权限决策和事务边界，协议负责人定义必要跨进程消息，基础设施负责人在其任务范围内实现 Core 定义的端口；控制 API 不直接操作存储或插件。

**建议接口与语义**：

- 定义权限决策服务，或可信授权上下文的签发、校验与失效机制；拒绝返回 `PERMISSION_DENIED`。
- 定义 Core 业务变更、幂等记录和审计的事务关系；明确 API 本地登录、刷新和撤销的审计持久化责任，以及失败/拒绝请求的记录方式。
- 定义事件流顺序、保留期、恢复游标、过滤、权限变化，以及与 REST 快照水位的衔接；定义不可恢复缺口的错误。

**验收**：

- [ ] 授权拒绝不产生业务副作用；业务变更、幂等和审计在失败及重试时符合确认的事务语义。
- [ ] 事件恢复、权限变化和快照衔接与 AsyncAPI 验收一致；插件无法获得管理员 token。

## 文档同步、验证和重新冻结

契约负责人变更 REST 或 WebSocket 时，同步 `doc/06-control-api.md`；涉及 Protobuf 时检查 `proto/README.md`、`doc/01-contracts.md` 和 `doc/02-core.md`；涉及事件投递、恢复或幂等时同步 `doc/01-runtime-semantics.md`。如变更影响运行配置、健康或部署，再同步 `doc/08-operations.md`。其他不直接描述受影响行为的模块文档无需为本任务改写。

在重新冻结前，契约负责人应运行 OpenAPI 和 AsyncAPI 解析、lint 与客户端生成兼容性检查；Protobuf 变更需运行 descriptor 兼容性、生成和跨语言 round-trip 测试。Core 和控制 API 负责人分别运行其模块构建与本清单中的正常、拒绝、重复、超时和依赖故障测试。具体命令按仓库当时的工具链与测试目标记录在各自交付说明中；不可用工具必须说明原因和风险。

所有 P0 的接口形状、权限、错误和验收条件确认并重新冻结后，控制 API 负责人可继续第一阶段实现；P1 的真实 Core 对接在其公共接口和实现就绪后进行。
