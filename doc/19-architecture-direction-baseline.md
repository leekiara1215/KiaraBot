## 1. 与首版设计及现行契约的关系

首版 [目标架构基线](18-architecture-baseline.md) 原文保留，不替换、不覆盖、不追加修改其受保护内容。本文件独立记录本轮确认结论，并在后文补充当前实现与演进方向。

继续保留首版的协议优先、Core 独立、适配器可替换原则：平台转换留在适配器，插件通过 SDK，面板通过 API，业务规则由拥有该业务的 Core 应用能力执行，基础设施实现端口。

本文件的进程拆分、持久化演进与现有同进程/快照实现不同。下文明确区分当前实现和已确认目标；不以新方向声称实现已经改变。

跨进程与跨语言契约仍以 `proto/` 为唯一来源，浏览器 REST/WS 契约仍以 `api/openapi.yaml`、`api/asyncapi.yaml` 为唯一来源。管理协议、错误码和数据库版本不能仅由本文件创设。现行模块文档继续说明现有行为；本轮方向的落地须经过详细契约、模块说明、实现和验证。

本文件未加入 AGENTS.md 的受保护文档清单，不改变首版基线的保护状态。

## 2. 已确认的方向结论

### A01：控制管理独立服务（方案 C）

控制管理拆为独立服务，通过明确的服务协议与 Core 交互，独立部署和生命周期管理成为目标。

插件运行服务不再依赖控制服务内部头文件或私有持久化文档。跨进程交互不能继续依赖同进程对象引用。

本项未确定控制管理服务的数据所有权、全部认证职责、管理 RPC 方法、授权执行点或一致性机制。这些须在详细设计中明确，不能据进程拆分将 Core 业务规则随意转移到控制服务。

### A02：独立 Repository 与关系表（方案 C）

持久化转向独立 Repository 与关系表，替换以完整 RuntimeSnapshot、单行 BLOB 和全局 revision 为中心的设计。

Core 通过端口表达数据访问与用例事务，基础设施负责数据库、SQL、连接与迁移实现。业务规则不进入数据库适配器。

数据模型、表结构、Repository 粒度、Unit of Work、索引与唯一约束须统一设计；状态变更、幂等记录和审计的原子性不得在拆分时丢失。

本项未指定 SQLite 或 PostgreSQL 等最终产品，也未决定每服务独库。旧快照读取、数据转换、切换、备份与回滚属于迁移设计，不能直接删除旧存储路径。

### A03：按服务划分独立进程（方案 C）

按职责划分服务，并以独立进程运行，目标超出单纯拆分 CMake 构建库。A01 的独立控制管理服务是其中明确的一项。

服务边界根据业务能力、状态所有权和故障隔离确定，不将每个现有类或每个函数自动拆成进程。具体服务清单、数量与通信拓扑尚未确定。

进程之间通过契约通信，不共享进程内指针、锁或事务对象。拆分后的身份、超时、取消、启动依赖、健康、幂等、重试和故障恢复按本轮相关裁定展开详细设计；具体协议和参数尚未定稿。

### A04：服务内部模型完全独立于协议类型（方案 C）

服务的领域层、应用层及内部业务端口使用自有命令、结果、错误和业务模型，不依赖 Protobuf/gRPC 生成类型、JSON 库或 HTTP 类型。原方案 B 的协议类型适度复用结论已被用户改选方案 C 取代。

Protobuf、JSON 和 HTTP 类型仅用于协议适配边界；边界完成校验、双向转换、序列化与反序列化。开放插件配置在传输中可以使用 Struct，但进入应用层时转换为内部配置表示，不直接传递 google::protobuf::Struct 或 nlohmann::json。

HTTP 状态、响应头、CORS、浏览器 JSON 与 WebSocket envelope 映射属于传输边界。内部错误和状态需与公共稳定码明确映射；不能因此另造互不兼容的错误语义。

服务身份与最终用户上下文必须有明确的信任来源；不能将浏览器自报用户或角色直接作为 Core 的可信身份。认证绑定方式和具体授权链路仍待管理协议设计。

本项适用于后续目标架构，当前 ports.hpp 等使用生成协议类型的代码尚未改造。具体内部类型、转换映射、生成代码链接范围及覆盖未知字段/枚举的兼容测试须在详细设计中明确。

### A05：生产显式迁移，启动默认验证（方案 B）

生产初始化、升级通过显式迁移命令执行；Core 默认验证数据库版本与可用性，匹配后才进入业务运行。开发自动迁移必须显式选择。

迁移逻辑保留唯一实现，命令与运行服务不各自复制一套迁移规则。首次安装必须具备显式初始化路径。

结合 A02/A03 设计各服务的迁移权限、顺序与版本检查，纳入适配器独立数据库及一致备份恢复；具体升级协调与回滚方案尚未定稿。

### A06：保留首版，补充本轮方向（方案 B）

保留首版设计；继续采用有依据的职责映射和契约来源，包括 `proto/`、`core/ports/`、`infrastructure/`、`doc/` 以及分开的 OpenAPI/AsyncAPI。不为字面目录一致而制造重复契约。

本轮结论在本文件独立记录，后文保留当前实现对照。首版 doc/18 不改；不建立相互竞争的线协议来源。新增裁定经用户确认后增补本文件，裁定清单仅保留确认结论索引。

既有 T12 延期决定继续有效；独立服务方向不自动授权实施 C++ 适配器、C ABI 或其他未确认扩展。

### D02：首期支持跨主机分布式部署（方案 C）

本轮独立服务从首期支持跨主机运行，不将支持范围限定为 Linux 单机回环或单机容器网络。控制管理独立进程已由 A01/A03 确认，本项明确其部署拓扑可跨主机。

服务寻址、受控监听、服务身份认证、加密通信、连接恢复与版本协同纳入详细设计。现有回环限制和 Linux host-network Compose 只能作为当前实现或本机部署方式，不能作为跨主机目标已经完成的证明。

验收需覆盖跨主机调用、依赖超时、断网与恢复、重复请求、部分服务不可用及分阶段升级。不以同机两个进程互调替代跨主机验证。

本项不自动确定 Kubernetes、注册中心、消息中间件或具体 TLS 方案，也不自动承诺 Core 多副本、多写入者、自动故障切换或高可用；这些须分别确定一致性、所有权和验收条件。

### D03：本轮完成核心运行管理（方案 C）

本轮管理范围覆盖现有管理入口的真实闭环，并增加运行所需的核心管理能力。此方案为用户本次确认的“核心运行管理”方案 C，不是早期已移除的“只读面板”选项。

| 管理能力 | 本轮确认范围 |
| --- | --- |
| 插件 | 完善已有启停、配置、校验入口及其运行结果闭环 |
| 登录会话 | 完善已有查询、撤销及权限生效行为 |
| Action | 补齐现有查询的真实数据来源、调用方隔离、保留与过期语义 |
| 运行状态 | 完善现有状态展示，区分配置状态、实际运行状态与操作结果 |
| 机器人账号与适配器 | 增加账号及适配器绑定管理 |
| 模型 | 增加模型配置及密钥更新管理 |
| 群白名单 | 增加在线管理 |
| 定时任务 | 提供查询与取消 |

消息历史、会话上下文编辑、插件市场等不进入本轮范围，后续另行排期。用户/角色管理范围按已确认 D05 执行：本轮保留固定角色、支持资源范围授权，自定义角色管理后续排期。

新增管理用例须先定义服务协议和 OpenAPI/AsyncAPI，再实现服务及页面；管理命令交给拥有相应业务状态的服务执行，控制服务不绕过协议直接修改其他服务数据库。

账号、模型密钥、白名单等更新的授权、审计、配置版本、并发冲突和生效时机（立即、重连或重启）须在详细设计中明确。独立服务、多账号或完整 RBAC 的具体运行能力不能仅凭存在管理页面认定完成。

本轮范围已确认，尚未实现与验收，不代表现行 API 已具备新增端点。

### D05：多业务实例与资源范围授权（方案 C）

本轮完成多业务实例运行及资源范围授权，保留固定角色；自定义角色管理后续排期。本项采用本轮聊天细化后的方案 C，不是早期“永久单实例和固定角色”的选项。

支持多个机器人账号、适配器连接及插件运行实例的装配、路由、启停和健康状态。每个实例具有独立配置的身份、凭据、权限范围和生命周期。

固定角色配合明确的资源范围约束，例如 operator 仅能操作获授账号或插件。暂不提供任意创建自定义角色、自由组合角色权限或复杂授权继承的完整管理系统。

插件类型、运行实例、连接身份须分别标识；凭据可逐实例撤销，不以共享全局万能凭据替代隔离。不同账号、适配器与插件实例之间不得串发或越权。

权限撤销的生效期限、现有会话与连接的失效、在途操作的处置、授权缓存与不可验证时的拒绝行为必须在详细契约中明确，不能因暂缓自定义角色而遗漏。用户管理入口的具体操作集合亦须在详细设计中列明，不据本项推断完整用户管理已经批准或完成。

本项多实例指业务实例，不自动承诺服务多副本、多写入者或高可用。身份注册、授权变更与作用范围等新增接口须遵守 A04 的内部模型隔离及 D02 的跨主机信任边界。

验收覆盖多实例并行、目标路由隔离、跨资源拒绝、逐实例凭据撤销、健康与生命周期隔离、权限失效及授权依赖故障。当前实现尚未改造。

### D07：结合新架构统一整理端口（方案 C）

以新架构的用例、内部模型、Repository 和事务设计为依据，逐项决定现有端口的保留、改造、替代或移除，避免新旧事务抽象长期并行。

新架构需要的能力重新定义或改造接口，并完成真实接线。被替代的旧端口须在检查生产代码、测试、文档和外部使用方后迁移、移除，不能仅根据未接线或引用数量机械删除。

FileStorage 暂不接入生产，不据此增加文件上传、附件或远程文件服务等业务范围；能独立复用的实现可以保留，并明确生产未接线状态。

存储端口表达服务内部数据访问，不因独立进程方向而自动成为远程数据库服务；审计改造必须明确业务写入的可靠性和事务边界，不能将原有原子审计简单替换为可能丢失的远程调用。

结合 A02/A04，新的内部存储与事务端口使用独立内部类型，协议转换放在边界。实施交付须列出每个端口的去留、替代关系、消费用例、事务归属和验证方式。

本项批准整理方向，尚未批准删除某个具体端口，也不代表现有接口已经完成迁移。

### D06：最小内容策略与平台异常闭环（方案 B）

本轮完成明确、可测试的最小内容规则，以及主要平台异常的稳定错误、运行状态和处置闭环。不重复建设已有权限、速率窗口与每日预算能力，不据本项扩展为完整审核平台。

Core 应用能力决定业务内容规则及是否允许派发；适配器识别平台响应与连接信号并转换为统一语义；控制管理服务展示原因并提供获授权的暂停、恢复入口；插件处理明确拒绝，不绕过 Core 调用平台。

详细设计须覆盖：内容拒绝不调用平台；登录失效或需要验证时停止受影响账号派发；明确限频按约定退避；执行结果未知时保留不确定语义，不盲目重发有副作用的动作；区分自动恢复和人工处置条件。

异常按账号或适配器实例隔离，避免单一账号异常无条件停止整个系统。具体暂停范围、在途操作处置和恢复权限须结合 D05 定义。

本项确认建设范围与职责，不直接批准任意内容过滤规则。实施前须提交具体规则、作用对象、平台信号、稳定错误与 retryable 映射、状态转换和恢复条件。新增错误码、健康状态及重试语义同步公共契约、模块文档与测试。

验收覆盖允许、拒绝、超时、平台依赖故障、未知执行结果、实例隔离及恢复路径；现有实现尚未因此改变。

### D01：危险动作显式启用与必需策略（方案 B）

本轮按动作分级，首先对 Mute/Kick 要求显式启用、目标群白名单和正每日预算，缺任一必需配置即拒绝，不派发平台动作。权限、D05 资源范围授权以及滑动窗口限流仍须同时通过，动作策略不能替代授权。

Delete 保留本 bot 已发送消息限制；Approve 保留仅好友请求限制，不直接套用群白名单。其他动作的附加策略另行具体定义，不据本项将全部 Action 改为同一套强制白名单与预算。

每日额度具体数值由部署策略确定；既有部署需补齐必需配置及升级说明。面板应显示未启用、配置缺失、目标不允许和预算耗尽等明确原因，错误语义须与契约一致。

详细设计须明确预算的动作/账号/目标作用域、检查与占用的原子性、幂等重放不重复占用、策略撤销对待派发动作的影响，以及明确失败或执行结果未知时的预算处置。不将这些尚待设计的细则视为已有实现。

验收覆盖缺配置拒绝、合法范围允许、越界拒绝、并发预算、幂等重放、跨重启持久化及拒绝无平台副作用。

### D04：内部命令幂等至少保留七天（方案 B）

内部成功命令的幂等记录至少保留七天，容量不足时拒绝新命令并提供明确错误与容量告警，不提前淘汰仍在承诺期内的记录。此期限按本轮提交用户确认的方案 B 及七天建议记录。

同一主体、操作和资源作用域内，同键同内容重放原处理结果，同键不同内容返回冲突；重放前重新鉴权，不能凭旧收据绕过权限撤销。业务修改、成功收据与必要审计在同一事务提交，并处理同键并发竞争。

本项只裁定内部命令，不自动改变控制 API 24 小时、Host 七天等现有不同作用域的期限。跨服务各执行边界须明确自己的幂等作用域，不只依赖入口去重。

详细设计须确定期限起算点、时钟与过期判断、持久化字段及索引、容量拒绝语义和清理机制；旧记录没有时间字段，迁移必须明确定义保守规则，不猜测创建日期。

过期后相同键可能被视为新命令，调用方不能无限期重试；外部执行结果未知时不能因收据过期就盲目重发。固定保留期不构成平台端到端 exactly-once 保证。

验收覆盖正常重放、内容冲突、权限撤销、并发重复、事务失败、跨重启、过期、容量耗尽和旧数据迁移。当前尚未实现该固定期限承诺。

### D08：投递尝试编号与受限续租（方案 C）

为插件事件投递增加独立尝试身份，ACK、续租及过期判断必须绑定当前有效尝试。event_id 在重投时保持不变用于业务幂等，尝试编号用于区分执行批次，不能互相替代。

旧尝试的延迟 ACK 不得确认后续尝试；无效或过期续租不能延长当前处理。长回调可申请续租，但须有明确总时长上限及续租约束，防止无限阻塞。默认租期、最大时长、续租频率及旧 ACK 的具体响应尚待详细设计。

断线或租约到期后按持久化规则恢复；租约失效不表示旧插件已经停止执行。外部副作用仍须业务幂等，尝试编号和续租不保证端到端只执行一次，也不能撤销已发生的平台操作。

协议、Core、SDK、持久化和特性协商共同升级，并明确旧客户端兼容与拒绝行为。结合 A02/A04，租约与尝试状态使用内部模型，边界映射到协议。

实施前定义 ACK/续租与超时竞争的原子判定、跨主机时钟依据、重启恢复、尝试唯一性和状态保留；验收覆盖延迟旧 ACK、重复 ACK、过期续租、续租上限、断线重连、崩溃恢复、并发竞争与死信。

当前 30 秒默认超时及现有协议仅为当前实现，不以本项声称新机制已上线。

### A07：认证注册元数据与能力协商（方案 B）

适配器的实现类型、版本及声明能力来自已认证连接的注册信息，服务端验证实例身份与账号绑定、校验元数据及协议版本，协商并保存有效注册信息，供查询和面板展示。移除控制投影中固定 nonebot2 的实现假设，不根据实例 ID 或名称推测类型。

实例身份和账号绑定以服务端可信配置或注册授权为准；适配器声明能力不构成权限授予。协商有效能力由双方支持范围及服务端策略决定，执行 Action 仍须通过权限、资源范围、白名单、预算等独立检查。

在线状态来自当前有效连接与健康检测；最后有效注册元数据可在断线后保留，但须与当前在线状态区分。未知类型明确表示未知，不伪装为 NoneBot2。公开元数据及状态投影不得泄露凭据。

详细设计须确定注册更新、重连后的能力变化、版本兼容和过期连接隔离规则；现行协议缺字段时先评估兼容扩展，不能仅修改展示文本。

验收至少包含两种模拟适配器、多实例、非法身份、能力不兼容、断线、重连和版本变化。本项不要求新增真实平台适配器，既有 T12 延期不变。

### D09：按权威契约和确认目标逐项统一（方案 B）

对传输行为建立“现行契约—实际行为—确认目标—实现与验证”矩阵。已有明确契约的实现偏差按缺陷修复；过时文档按证据修正，不反向推断实现缺失；契约未定义或新架构新增的行为先提出具体语义并确认，再登记与实施。

核对范围包括 HTTP 方法/状态/头/认证/错误结构、CORS、WebSocket 首帧与订阅授权/关闭/恢复、服务间身份与用户上下文、期限与取消、幂等重试、插件尝试编号与续租、兼容协商、升级顺序及 request_id/trace_id 传播。

不以框架默认值代替契约，不以当前实现直接覆盖已有承诺，不据本项自动开放跨域、全部 HTTP 方法或其他未确认扩展。CORS 来源和凭据、续租上限等具体参数仍需详细设计。

验收包括契约解析/lint、兼容性检查和成功、拒绝、超时、依赖故障、断线恢复等行为测试；文件可解析不等于实现满足契约。新增或修改语义按 AGENTS.md 在同一变更中同步唯一来源、直接相关模块说明和验证。

本轮确认的是收口方法；现行线协议、错误码与运行行为尚未因该裁定改变。

## 4. 方向之间的约束与实施前置

A01/A03 已确认控制管理独立服务，D02 已确认首期支持跨主机部署；不再将同进程或仅单机作为目标范围。具体监听、寻址、认证、加密和部署工具仍须详细设计。

A02 与 A03 需要共同确定状态所有权和本地事务边界。一个本地数据库事务不能直接延伸到多个服务；命令受理与执行完成、重试、幂等和失败恢复必须写入具体契约。本文件不预选分布式事务或消息中间件。

A04=C 要求协议类型与服务内部模型完全隔离；内部类型通过边界映射保持公共契约一致。服务之间不直接依赖彼此内部类或数据库表作为集成接口。

D03 确认的管理用例应作为服务接口与数据所有权设计的输入；跨主机部署和服务拆分不能替代管理功能闭环验收。

实施前必须补齐服务清单、输入输出、数据所有权、身份信任、稳定错误、超时取消、投递语义、存储迁移与回滚设计，再同步直接受影响的模块文档与测试。当前没有据此修改代码、线协议或生产配置。
