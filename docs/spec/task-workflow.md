# 任务工作流与协作规范

本文集中仓库的「任务如何拆、如何交付、文档如何同步」规范。编码规范见
[`coding-standard.md`](coding-standard.md)，模块边界见 [`boundaries.md`](boundaries.md)，
工具链与质量门禁见 [`toolchain.md`](toolchain.md) 与 [`ci-gates.md`](ci-gates.md)。

## 1. 可执行编码任务模板

“代码启动句”说明方向；真正开始编码时使用下面模板，把规格冻结到文件、命令和验收条件。

```markdown
# 任务：<模块>/<功能>

## 目标
一句话说明要交付的可运行能力。

## 允许修改
- <明确文件或目录>

## 禁止修改
- <明确目录>
- 不改变已发布的 proto 字段编号
- 不增加跨层反向依赖

## 契约
- Protobuf：<文件和 message/service>
- OpenAPI：<路径和 schema>
- AsyncAPI：<频道、首帧或消息 envelope；不涉及则写“不涉及”>
- 输入、输出和稳定错误码：<完整列表>
- HTTP/gRPC 状态、健康/生命周期状态：<映射和完整列表；不涉及则写“不涉及”>

## 文档同步
- 必须更新：<架构/模块/规范/运维和测试文档路径>
- 无需更新：<已检查但不受影响的文档及理由>
- 唯一来源和更新顺序：<先协议/API，再模块语义，后实现和测试>
- 文档校验命令：<YAML lint、descriptor diff、代码生成或其他命令>

## 运行语义
- 顺序、投递、重试、幂等和超时：<明确数值>

## 依赖和命令
- 编译器与库版本：<版本>
- 生成命令：<完整命令>
- 统一工具链和质量检查：`./scripts/check-toolchain.sh`
- 构建和测试命令：<完整命令；单项检查见 spec/toolchain.md>

## 验收标准
- [ ] <正常路径>
- [ ] <故障路径>
- [ ] <边界路径>
```

## 2. 开发前必须确认

- 先确定任务所属模块和允许修改的目录；
- 先阅读相关协议、架构、模块责任与工具链规范；
- 不跨模块修改内部实现，不绕过公共协议和端口接口；
- 不把生成文件、构建产物、密钥或本机配置提交到仓库；
- 修改 C++ 后运行与变更相关的构建、测试和格式检查。

## 3. 规则优先级

1. 用户在当前任务中明确提出的要求；
2. 根 [`AGENTS.md`](../../AGENTS.md) 与 [`coding-standard.md`](coding-standard.md)；
3. [`boundaries.md`](boundaries.md)、[`architecture.md`](../architecture.md) 与对应模块文档；
4. 现有代码的局部惯例。

当现有代码与主规范冲突时，不要顺手进行大范围格式化；只在当前任务涉及的范围内遵守主规范，
并在变更说明中指出冲突。

## 4. 交付要求

每个实现任务都应说明：目标模块、输入输出、错误语义、允许修改的文件、构建命令、测试命令和
验收条件。完成修改后，报告实际运行过的检查及未运行检查的原因。

交付说明必须包含：文档影响判断、实际更新的文档路径、未更新但已判断无需更新的文档及理由、
文档校验命令和结果。

## 5. 文档同步规则（AI 强制）

代码任务开始前，AI 必须先做一次“文档影响判断”。只要代码改变了外部可见的接口、协议、状态、
错误语义、配置、运行方式或模块责任，就必须在同一变更中更新对应文档和验证；不能只改实现或
只改测试。

### 文档范围与唯一来源

| 变更内容 | 必须检查或更新的文档 | 契约唯一来源 |
| --- | --- | --- |
| Protobuf message、service、字段、枚举、版本或兼容性 | `proto/kiarabot/v1/`、`docs/architecture.md`（契约总览）；涉及投递、重试、幂等时同步 `docs/architecture.md` 运行语义章节 | `proto/` |
| REST 路径、方法、请求/响应 schema、分页、认证或 HTTP 状态码 | `api/openapi.yaml`、`docs/modules/control-api.md`，以及受影响的模块文档 | `api/openapi.yaml` |
| WebSocket 频道、首帧、消息 envelope、事件类型、重连或流状态 | `api/asyncapi.yaml`、`docs/modules/control-api.md`；涉及投递语义时同步 `docs/architecture.md` | `api/asyncapi.yaml` |
| 稳定错误码、错误结构、HTTP/gRPC 映射、健康/生命周期状态 | 产生该语义的协议或 API 契约、`docs/architecture.md`、对应模块文档和错误/状态测试 | 产生该语义的协议或 API 契约 |
| Core、PluginSDK、适配器、基础设施或面板的公共行为、边界、输入输出 | 对应的 `docs/modules/*.md` 模块文档，以及协议/API 文档（若跨边界） | 对应公共接口或契约 |
| 启停、健康检查、迁移、日志字段、备份、告警或部署配置 | `docs/modules/infrastructure.md`、`docs/spec/ci-gates.md`、`README.md` 部署章节和 API 健康契约 | 运维接口或配置定义 |

“对应文档”只包括直接描述被修改行为的契约、模块、运行语义、运维和测试文档；不要求为了一个
局部实现改动重写无关的架构说明、路线图或示例。

### 更新顺序和一致性要求

1. 先确定公共契约和错误/状态语义，更新唯一来源；跨模块变更遵守“先协议/接口、后实现、再测试”。
2. 再更新对应模块文档中的责任、输入输出、时序、权限、超时、幂等和失败行为；文档中的示例、
   枚举和状态名必须与契约逐项一致。
3. 最后更新实现、测试和生成配置。生成的 `.pb.*`、客户端代码和构建产物不得手工编辑或提交。
4. 新增或修改错误码、HTTP/gRPC 状态、健康状态或生命周期状态时，必须同时更新跨边界映射、
   客户端可见说明和覆盖正常/拒绝/超时/依赖故障路径的测试；自由文本错误消息不能替代稳定码。
5. 协议/API 文档改动必须运行对应解析、lint、代码生成或 descriptor/兼容性检查；若工具链当前
   不可用，交付说明必须写明未运行原因和风险。

### 更新边界与豁免

- 只修改当前任务所属模块和直接受影响的共享契约文档；不得借机整理无关文档或改变未涉及的模块边界。
- 纯内部重构、局部格式调整、仅测试重排、生成物变化，以及不改变输入输出、错误、状态、配置、
  时序或权限的实现细节，可以不新增文档，但交付说明必须明确“无文档影响”。
- 任何跨进程、跨语言、控制面板、插件 SDK 或运维接口的可观察变化都不能按内部改动豁免。
- 文档与代码冲突时，以当前任务确认的公共契约为准；应在同一变更中修正文档和实现，不得用注释
  掩盖不一致。

## 6. 受保护文档

- 当前清单为空：原人类冻结基线 `docs/architecture.md` 已按维护者授权并入
  [`docs/architecture.md`](../architecture.md)，冻结事实保留在该文档的架构章节。
- 受保护文档（如后续重新指定）不适用“文档同步规则”：AI 不得以同步为由编辑它，必须在交付说明中
  列出差异由人类维护者决定。跨语言契约仍以 `proto/` 为准，HTTP/WebSocket 契约以 `api/` 为准。
- 未经人类维护者在当前任务中明确授权，AI 不得把任何文档加入或移出受保护清单。
